# 개발 서버와 검증 환경

AI가 변경을 확인하려고 개발 서버를 하나 더 띄우면 **사용자가 쓰던 서버가 망가진다.**
2026-09-05부터 09-07까지 세 번 겪고 원인을 두 단계로 찾았다. 이 노트는 그 결말이다.

## ⚠️ 원인 ① — 같은 `.next` 를 공유한다

서버 둘이 같은 `.next` 를 쓰면 서로의 청크를 지운다. 화면은 뜨는데 스크립트가
404로 떨어지고, 결국 응답이 멈춘다.

## ⚠️ 원인 ② — `tsconfig.json` 을 고쳐 쓴다 (이게 진짜였다)

`.next` 를 분리하고도 또 먹통이 됐다. **Next 는 `tsconfig.json` 의 `include` 에
자기 distDir 의 타입 경로가 없으면 그 파일을 고쳐 쓴다.**

`npm run dev:verify` 를 띄울 때마다 `.next-verify/types/**/*.ts` 가 추가되고,
그 **쓰기 한 번이 돌고 있는 개발 서버를 재시작시킨다.** 반복되면 멈춘다.

증상이 특이하다 — 프로세스는 `LISTENING` 인데 `curl` 이 **000** 을 돌려준다.
`netstat` 으로는 살아 있어 보이므로 응답 코드를 꼭 확인한다.

```bash
netstat -ano | grep LISTENING | grep -E ":300[0-5]\s"
curl -s -o /dev/null -w '%{http_code}' -m 20 http://localhost:3003
```

### 해결 — 타입 경로를 미리 넣어 커밋한다

이미 있으면 Next 가 다시 쓰지 않는다. 여섯 앱 모두 이렇게 커밋돼 있다.

```json
"include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts",
  ".next-verify/types/**/*.ts", ".next-build/types/**/*.ts"]
```

**이 두 줄을 지우면 함정이 돌아온다.** `next.config.ts` 와
`scripts/dev-verify.mjs` 주석에도 같은 경고를 남겼다.

## 검증용 서버 — 앱마다 따로 있다

`npm run dev:verify` 가 `.next-verify` 에 따로 쌓는다.
`distDir` 은 `next.config.ts` 가 `NEXT_DIST_DIR` 을 읽어 정한다.
(윈도우 cmd 는 `VAR=x cmd` 형식이 안 먹어서 `scripts/dev-verify.mjs` 로 감싼다.)

| 앱 | `npm run dev` | `npm run dev:verify` |
|---|---|---|
| MyJane | 3000 | **3010** |
| SnapWord | 3001 | **3011** |
| SnapNote | 3002 | **3012** |
| FitLog | 3003 | **3013** |
| 2hbk | 3004 | **3014** |
| TypeLog | 3005 | **3015** |

`C:\Dev\.claude\launch.json` 에 `<app>-verify` 항목이 있다.
2026-09-07 이전의 `2hbk-verify`·`typelog-verify` 는 **`.next` 를 공유하고 있었다** —
이름만 verify 였다. 새로 만들 때 `run dev:verify` 를 가리키는지 확인할 것.

## 개발 서버가 떠 있을 때

- **타입 검사**는 `npx tsc --noEmit`. 아무 파일도 건드리지 않는다.
- **빌드**는 `NEXT_DIST_DIR=.next-build npx next build`. 끝나면 `.next-build` 를 지운다.
  타입 경로를 미리 넣어둔 뒤로는 `tsconfig.json` 이 더러워지지 않는다.
- `next lint` 는 쓰지 말 것 — 대화형으로 멈추고 `tsconfig.json` 을 고쳐 쓴다.

## 사용자 서버가 며칠씩 떠 있다

2026-09-07에 확인해 보니 여섯 개가 전부 응답하지 않았고, 프로세스 시작 시각이
**9월 4~5일**이었다. 오래 떠 있던 서버는 그 사이의 파일 변경이 쌓여 이미
망가져 있을 수 있다.

AI가 원인일 수도, 아닐 수도 있다. **응답 코드를 먼저 재고**, 먹통이면
재시작을 요청한다. 사용자 프로세스를 AI가 죽이지 않는다.

## 배포 확인 — Vercel 봇 차단

`curl` 로 배포를 반복 확인하면 Vercel 의 봇 차단에 걸린다.

```
HTTP/1.1 403 Forbidden
X-Vercel-Mitigated: challenge
X-Vercel-Challenge-Token: …
Title: Vercel Security Checkpoint
```

**배포 실패가 아니다.** 실제 브라우저는 통과한다. FitLog 에서 실제로 걸렸다.

- 정적 자산(`/favicon.png`)은 대개 통과한다 → 바이트를 로컬과 비교하면 배포 확인이 된다
- 그래도 막히면 브라우저로 열어 `getComputedStyle` 로 토큰 값을 읽는다
- 배포 전파는 앱마다 1~4분씩 다르다. 한 번 실패로 판단하지 말고 재시도한다

## 렌더 상태를 재는 도구 (CDP)

헤드리스 크롬에 **CDP 로 직접 붙으면** 실제 렌더 상태를 잴 수 있다.
Node 22+ 의 전역 `WebSocket` 을 쓰면 의존성이 필요 없다.

```
chrome --headless=new --remote-debugging-port=9355 --user-data-dir=<임시>
GET http://127.0.0.1:9355/json/version → webSocketDebuggerUrl
Target.getTargets → Target.attachToTarget → Page.navigate → Runtime.evaluate
```

대비 검사에 쓴 예가 [[먹청 톤 팔레트]]에 있다. 그때 겪은 도구 함정들:

- **Git Bash 가 `/login` 을 윈도우 경로로 바꾼다** (`C:/Program Files/Git/login`).
  아무것도 재지 않고 "미달 0건"이 나온다 — 거짓 통과다.
  `MSYS_NO_PATHCONV=1` 을 붙이고 **검사한 개수를 함께 출력**해 0이 아닌지 본다.
- 크롬이 색을 `color(srgb 0.98 0.97 0.94)` 로도 돌려준다. 그 **0~1 값을 0~255 로
  착각**하면 거의 검정으로 계산돼 오탐이 쏟아진다.
- 브라우저에 **문자열로 넘기는 코드**에서는 정규식 이스케이프가 소실된다
  (`/^color\(/` → `/^color(/`). 정규식을 문자열 검사로 바꾸는 편이 안전하다.
- 스크린샷은 Browser 패널 높이에 따라 합성이 깨진다. 전체 화면이 필요하면
  `chrome --headless --screenshot --window-size=W,H` 로 따로 찍는다.
