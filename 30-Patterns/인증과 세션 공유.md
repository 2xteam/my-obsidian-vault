# 인증과 세션 공유

myjane.co.kr의 서비스들(SnapWord · SnapNote · FitLog · 2hbk)은 **회원을 공유**한다.
공유하는 것은 회원과 세션까지다. 데이터·화면·소개 문구는 나눈다
→ [[서비스 카테고리와 카피 원칙]]
한 번 가입하면 네 앱을 모두 쓴다. 단 **로그인 수단은 앱마다 다르다** — 아래 참조.

## 구조

```
MongoDB Atlas / Cluster0
├─ user        ← users 컬렉션 (네 앱 공용)
├─ vocab       ← SnapWord 데이터
├─ math        ← SnapNote 데이터
├─ fit         ← FitLog 데이터
└─ hamhibokka  ← 2hbk 데이터
```

앱은 각자 자기 DB에 붙지만, 회원만 `user` DB를 본다.

```ts
// models/User.ts
export function getUserModel(): Model<UserDocument> {
  const dbName = (process.env.MONGO_USER_DB ?? "user").trim() || "user";
  const userDb = mongoose.connection.useDb(dbName, { useCache: true });
  return userDb.models.User ?? userDb.model("User", UserSchema, "users");
}
```

`connectDB()` 완료 후에 호출해야 한다.

## 로그인은 입력칸 하나로 (2026-09-03)

앱마다 로그인 수단이 갈렸다 — Snap 계열·FitLog는 전화번호+PIN, 2hbk는 자체 백엔드에서
이어받은 이메일+비밀번호. 처음에는 포털 화면을 둘로 갈랐는데, 사람에게 **"당신은 어느 쪽
회원이냐"를 묻는 셈**이라 하나로 합쳤다.

```
이메일 또는 전화번호  ─┐
                      ├─ 맞는 것으로 들어온다
비밀번호 또는 PIN    ─┘
```

- `lib/identifier.ts` — `@`가 있으면 이메일, 숫자 9~11자리면 전화번호
- 계정마다 `password`와 `pin` 중 **있는 것으로 차례로** 맞춰 본다.
  둘 다 가진 계정(이메일이 겹쳐 병합한 1건)은 어느 쪽이든 통과한다
- 가입도 하나만 넣으면 된다. 이메일이면 `password`(8자↑), 전화번호면 `pin`(4자↑)에 들어가고
  그것이 그 계정의 로그인 수단이 된다
- 전화번호로 여러 계정이 있으면 409로 알린다(예전과 같다)

그래서 `users` 스키마에서 **`name`·`phone`·`email`·`pin`이 모두 선택 필드다.**
어느 칸이 채워졌는지가 곧 그 계정이 쓸 수 있는 로그인 방식이다.

> 2026-09-07 부터 **새 가입은 이메일이 필수**다. 다만 그 필수는 가입 라우트에서만
> 걸고 **스키마는 선택 그대로 둔다** — 아래 "이메일 필수화와 인증" 참고.

> ⚠️ **네 앱의 `models/User.ts`를 함께 고쳐야 한다.** 한 컬렉션을 공유하므로
> 한 앱만 필수로 남겨 두면 그 앱의 `user.save()`가 `User validation failed: email`로
> 터진다. 전화번호만 있는 계정을 FitLog가 저장하려다 실제로 그랬다.

`/api/auth/login`은 **`pin`이 없는 계정을 건너뛴다.** 안 그러면
`bcrypt.compare(pin, null)`에서 터진다. 각 앱의 로컬 로그인 라우트도 같다.

## users 문서

공용 필드: `name` `phone` `email` `pin` `password` `tokens` `pinResetToken` `lastLoginAt`
이메일 인증(2026-09-07 추가, 여섯 앱 공용): `emailVerified` `emailToken`
`emailTokenExpires` `emailTokenSentAt` `emailPromptSnoozedUntil` `pendingEmail`

앱 전용 필드도 같은 문서에 둔다 —

- FitLog: `heightCm` `gender` `birthYear`
- 2hbk: `userId` `nickname` `profileImage` `followApprovalRequired`

`emailVerified` 는 원래 2hbk 전용이었다. 포털이 인증을 하게 되면서 공용으로
올려 썼다 — 값의 의미는 그대로라 2hbk 쪽 동작은 바뀌지 않는다.

다른 앱은 그 필드를 읽지도 쓰지도 않으므로 충돌이 없다.

> ⚠️ **2hbk의 `userId`는 도메인 식별자다.** 목표·팔로우·초대 문서가 Mongo `_id`가
> 아니라 이 문자열(`user_xxxxxxxxx`)을 참조한다. 바꾸면 데이터 전체가 끊긴다.
> 유일 인덱스는 **부분 인덱스**로 건다 — 다른 앱 회원은 이 필드가 `null`이라
> sparse로는 null끼리 충돌한다.
>
> ```js
> { userId: 1 }, { unique: true, partialFilterExpression: { userId: { $type: "string" } } }
> ```

## 세션 — 쿠키 도메인 공유

`snap_user` 쿠키에 세션을 담고, 도메인을 `.myjane.co.kr`로 설정해 서브도메인끼리 공유한다.

```ts
// lib/session.ts — 호스트가 쿠키 도메인에 속할 때만 domain 속성을 붙인다
const domain = ENV_COOKIE_DOMAIN.replace(/^\./, "");
if (host === domain || host.endsWith("." + domain)) return ENV_COOKIE_DOMAIN;
return undefined;   // *.vercel.app 등에서는 host-only 쿠키
```

덕분에 `*.vercel.app` 프리뷰에서도 로그인이 동작한다(공유만 안 될 뿐).

## ⚠️ 가장 흔한 실패

`NEXT_PUBLIC_COOKIE_DOMAIN`을 **Vercel Secret 타입으로 등록하면 동작하지 않는다.**
브라우저 번들에 값이 주입되지 않아 쿠키가 host-only가 되고, 앱 간 로그인이 끊긴다.
에러도 로그도 남지 않는다. → [[Vercel 배포 패턴]]의 "환경 변수 함정 ③"

## 통합 로그인 (2026-09-02 적용)

로그인·회원가입은 `www.myjane.co.kr`에서만 처리한다. 각 앱은 리디렉트만 한다.

```
앱 → https://www.myjane.co.kr/login?from=<앱키>&next=/home
   ← 포털이 .myjane.co.kr 쿠키를 저장하고 원래 앱으로 복귀
```

앱키는 `snapword` · `snapnote` · `fitlog` · `2hbk` · `typelog`.

> ⚠️ **`lib/apps.ts` 의 `APPS` 에 없는 앱키는 조용히 무시된다.** `getApp()` 이
> `null` 을 돌려주고, 그러면 `?from=` 도 `next=` 도 없던 것처럼 동작해 인증 후
> **원래 앱으로 돌아가지 못하고 포털에 머문다.** 오류도 로그도 없다.
> TypeLog 이 2026-09-07 까지 그 상태였다 — 앱을 새로 붙이면 여기부터 등록한다.
>
> `requiresSessionToken` 을 빠뜨리는 것도 조용하다. 그 앱의 API 가 서명 토큰을
> 검증하는데 이 표시가 없으면, 포털이 토큰 없는 세션을 그대로 돌려보내고
> **화면만 열린 채 API 가 전부 401** 이 된다. 지금 `2hbk` 와 `typelog` 이 그렇다
> (`<앱>/lib/auth.ts` 에 `verifySessionToken` 이 있으면 이 표시가 필요하다).

- 앱은 **운영 도메인일 때만** 포털로 보낸다.
  `location.hostname.endsWith(".myjane.co.kr")` 로 판단하며,
  로컬 개발에서는 자기 로그인 화면을 그대로 쓴다(localhost에는 쿠키 도메인이 안 붙는다)
- `next`는 경로만 허용한다. 오픈 리다이렉트 방지
- 가입 출처는 `users.signupFrom`
- 자세한 구성은 [[MyJane]]

## 쿠키의 id를 믿지 않는다 — 서명 토큰 (2026-09-03)

세션 쿠키는 **클라이언트가 읽고 고칠 수 있는 평문 JSON**이다. 그래서 그 안의 `id`를
그대로 믿으면 아무나 남의 계정으로 API를 부를 수 있다. Snap 계열과 FitLog는 개인
기록만 다뤄 드러나지 않았지만, 2hbk는 **남의 목표에 스티커를 붙이고 참가를 승인하는**
동작이 있어 그대로 둘 수 없었다.

쿠키 payload에 `token` 한 칸을 덧붙였다.

```
{ v: 1, user: {...}, token: "<base64url(claims)>.<base64url(hmac)>", expiresAt }
                     ^^^^^ 포털이 서명, 앱이 검증
```

- claims는 `{ uid: <_id>, u: <userId>, exp }`
- **모든 로그인 경로가 토큰을 발급해야 한다.** 전화번호+PIN 경로가 발급하지 않아
  "2hbk에서 로그인하면 FitLog가 되는데 반대는 안 되는" 한쪽 방향 문제가 있었다
- `userId`가 없는 옛 계정은 로그인할 때 채워 준다. 없으면 서명할 값이 없다
- 발급 `myjane/lib/sessionToken.ts` · 검증 `2hbk/lib/auth.ts`
- **두 배포가 `SESSION_SECRET`을 같은 값으로** 가져야 한다. 다르면 전부 401
- 서명 길이가 다르면 `timingSafeEqual`이 예외를 던지므로 먼저 길이를 본다
- 다른 세 앱은 모르는 필드라 무시한다 → **기존 세션과 그대로 호환된다**

확인한 동작 — 정상 토큰 200 / 서명 변조 401 / 토큰 없음 401 /
쿠키의 `id`만 남의 것으로 바꾸고 토큰 없이 401.

### ⚠️ 로그인 무한 왕복 (2026-09-03에 겪음)

**증상** — 로그인은 성공하는데 앱 화면이 다시 로그인으로 보내고, 로그인은 다시
화면으로 보내며 끝없이 오간다.

**원인** — 로그인 여부를 **두 곳이 서로 다른 기준으로** 판단했다.

| 자리 | 기준 |
|---|---|
| 앱 화면 게이트 | 사용자 + **서명 토큰** |
| 로그인 화면 · 포털 | 사용자만 |

토큰 없는 세션(= 전화번호+PIN 앱에서 만든 세션)을 들고 2hbk에 가면 게이트는
"못 쓴다"고 로그인으로 보내고, 로그인은 "세션 있네"라며 화면으로 돌려보낸다.

**대응** — 세 가지를 함께 넣어야 끊긴다.

1. **판단 기준을 하나로.** 2hbk는 `hasUsableSession()`(사용자 + 토큰) 하나만 쓴다
2. **`relogin=1`.** 게이트가 못 쓰는 세션을 만나면 이 표시를 붙여 보내고,
   포털은 이 표시가 있으면 세션이 있어도 **폼을 보여준다.** 포털은 추가로
   `usesEmailLogin` 앱인데 토큰이 없으면 역시 되돌려보내지 않는다
3. **왕복 횟수를 센다.** `sessionStorage`에 세어 3회를 넘으면 이동을 멈추고
   안내 화면과 "로그인 정보 지우고 다시 로그인" 버튼을 보여준다.
   예상 못 한 조합에서 또 왕복하더라도 **무한 이동이 아니라 눈에 보이는 화면**으로 끝난다

### ⚠️ 포털과 앱의 `SESSION_SECRET` 이 **둘 다** 있어야 한다

2026-09-03 운영에서 2hbk 프로젝트에만 넣고 포털에는 빠뜨렸다. 증상은
가입·로그인 화면의 `SESSION_SECRET 환경 변수가 없거나 너무 짧습니다`다.

환경 변수는 **배포 시점에 스냅샷**되므로 추가한 뒤 **재배포**해야 한다
→ [[Vercel 배포 패턴]]의 "환경 변수 함정 ①"

값이 같은지는 대시보드에서 읽을 수 없다. 확인하려면

```bash
npx vercel env pull --environment=production <임시파일>   # 프로젝트마다
# 값을 출력하지 말고 sha256 앞 12자만 비교한다
```

### ⚠️ 세션을 다시 저장할 때 토큰을 떨어뜨리지 말 것

`saveSession(user)`를 토큰 없이 부르는 자리가 많다 — 프로필 이름을 고칠 때,
각 앱의 로컬 로그인 등. 그때마다 토큰이 사라져 2hbk 로그인이 조용히 풀렸다.

**토큰을 넘기지 않으면 이미 있는 것을 살린다.** 단 `user.id`가 다르면(사람이 바뀌면)
남의 토큰을 물려줄 수 없으니 버린다. 다섯 저장소의 `lib/session.ts`가 모두 같다.

### ⚠️ `snap_user` 쿠키가 둘일 수 있다

`.myjane.co.kr` 도메인 쿠키와 `<앱>.myjane.co.kr` host-only 쿠키가 함께 있으면
브라우저가 **둘 다** 보내고 순서는 기대할 수 없다. `document.cookie`를 첫 줄만 읽으면
낡은(토큰 없는) 쪽을 집어 위 왕복이 생긴다.

같은 이름의 쿠키를 **전부 모아 토큰 있는 것을 우선**해서 고른다
(`getCookieValues()` → `readBestPayload()`). 두 앱 모두 같은 방식으로 고쳤다.

### 관리자 권한

`users.adminRole`(`master` · `operator` · `null`)로 `/admin` 접근을 가른다.
확인은 여기서도 **세션의 서명 토큰**을 쓴다 → [[통합 admin]]

### 기록 API의 소유자 확인

`/api/*/[id]` 의 GET·PATCH·DELETE는 `{_id, userId}` 를 **함께** 조회한다.
id만 보고 고치거나 지우면 남의 기록 id를 넣어 건드릴 수 있다 → [[피검사 지식베이스]]

## 이메일 필수화와 인증 (2026-09-07)

가입은 **이메일 필수 · 전화번호 선택**으로 뒤집었다. 로그인은 그대로 입력칸 하나다.
자세한 결정은 [[B 로그인·회원가입 개편]].

### ⚠️ 필수는 스키마가 아니라 라우트에서 건다

`users` 는 여섯 앱이 공유하고 전화번호만 있는 계정이 남아 있다(2026-09-07 기준 4건).
`models/User.ts` 에서 `email` 을 `required` 로 바꾸면 그 계정들의 `user.save()` 가
**여섯 앱 전부에서** `User validation failed: email` 로 터진다. 다른 앱이
`lastLoginAt` 만 갱신해도 마찬가지다.

필수는 **가입 화면과 `/api/auth/register` 에서만** 건다. 여섯 `models/User.ts` 의
`email` 선언 위에 같은 경고를 주석으로 박아 두었다.

### 새 필드 — 여섯 앱에 같이 넣었다

```
emailVerified            2hbk 전용이었다가 공용으로 올렸다 (값의 의미는 그대로)
emailToken               forgot-pin 과 같은 모양. 30분 만료, 한 번 쓰면 폐기
emailTokenExpires        이름은 pinResetExpires 와 맞췄다 (계획서의 …ExpiresAt 대신)
emailTokenSentAt         재발송 쿨다운 60초의 기준
emailPromptSnoozedUntil  안내를 다시 띄울 시각. 하루에 한 번만 묻는다
pendingEmail             아직 인증되지 않은 새 주소
```

앱들은 대부분 읽지도 쓰지도 않지만 **선언은 여섯 곳에 다 둔다.** 한 컬렉션을
공유하므로 스키마에 없는 필드는 그 앱에서 저장할 때 유실될 수 있다.

### ⚠️ `update-email` 이 인증도 권한 확인도 없었다

고치기 전 `myjane/app/api/auth/update-email/route.ts` 는 두 가지가 빠져 있었다.

| 무엇이 | 어떻게 |
|---|---|
| 권한 확인 | **요청 본문의 `phone` + `userId`** 만 봤다. 쿠키조차 아니라, 남의 `userId` 와 전화번호만 알면 그 계정에 이메일을 심을 수 있었다 |
| 메일 인증 | 없었다. 받은 주소를 그대로 `user.email` 에 저장했다 |

두 번째가 특히 조용한 함정이다. 남의 주소를 자기 계정에 심어 두면 **그 주소의
진짜 주인이 가입할 때 "이미 가입된 이메일"로 막힌다.** 그래서 인증 전에는
`pendingEmail` 에 두고, `/api/auth/verify-email` 이 링크를 확인한 뒤에야 `email` 로
옮긴다. 옮기기 **직전에 중복을 한 번 더 본다** — 메일을 보낸 뒤 링크를 누르기까지
사이에 다른 사람이 그 주소로 가입할 수 있다(유일 인덱스가 없다).

가입은 다르다. 그때는 이메일이 곧 계정의 신원이라 바로 `email` 에 넣는다.

### 권한 확인은 한 곳에서 — `lib/serverSession.ts`

쿠키에서 서명 토큰을 꺼내 회원을 찾는 코드가 `lib/adminAuth.ts` 안에만 있었다.
admin 이 아닌 일반 회원 동작(이메일 등록·재발송·비밀번호 설정)도 같은 확인이
필요해서 `lib/serverSession.ts` 로 꺼내고, `adminAuth` 가 그것을 쓰도록 했다.
**두 벌로 두면 언젠가 한쪽만 고쳐진다.**

### ⚠️ 메일을 보내기 전에 토큰을 심지 말 것

`emailTokenSentAt` 을 먼저 얹고 메일을 보내면, 발송이 실패했을 때도 쿨다운이
남는다. 오지도 않은 메일 때문에 60초 동안 재발송이 막힌다. **보내고 나서 얹는다.**

### ⚠️ 가입 중 메일 발송 실패로 가입을 실패시키지 말 것

계정을 만든 뒤 메일 발송이 터졌다고 500 을 돌려주면, 계정은 이미 있는데 사람은
"가입 실패"를 본다. 다시 시도하면 이번엔 409(이미 가입된 이메일)가 나고,
메일도 못 받은 채 들어갈 수도 나갈 수도 없다. 2026-09-03 의
"서명 실패로 계정만 남는" 사고와 같은 모양이다.

계정을 살리고 `mailSent: false` 를 함께 돌려준다. 메일은
`/api/auth/send-verification` 으로 다시 받을 수 있다.

### 인증은 로그인 조건이 아니다

미인증 상태로도 로그인은 된다. 조건으로 걸면 메일이 늦거나 스팸함에 들어간
사람이 갇힌다. 대신 **포털에서만** 하루 한 번 안내 띠를 띄운다
(`components/EmailPrompt.tsx`). 여섯 앱이 각자 물으면 같은 사람에게 여섯 번 묻는다.

다섯 앱은 `components/EmailBanner.tsx` 로 **포털 링크만** 보여 준다. 판단은
세션 쿠키의 `email` 하나로 한다 — 인증 여부는 쿠키에 없고, 알려면 포털 API를
교차 출처로 불러야 한다. 안내 띠 하나 때문에 CORS 를 열지 않는다.

그래서 다섯 앱의 `SessionUser` 에 `email?: string` 을 더했다. **읽기만 한다.**
세션을 다시 저장할 때 빠뜨리면 안 되는 것은 `token` 과 같다.

### ⚠️ 새 불리언 필드를 켜는 기능은 기존 계정을 먼저 본다

`emailVerified` 는 기본값이 `false` 다. 인증 안내를 붙이자마자 **이미 이메일을
쓰고 있던 21명 전원에게** 안내가 뜰 상태였다. 기능은 맞는데 기존 사용자에게는
새로 생긴 잔소리다.

2026-09-07 에 이메일이 들어 있는 21건을 `true` 로 올려 정리했다. 지금 안내는
전화번호만 있는 4건에만 뜬다. 자세한 기록은 [[B 로그인·회원가입 개편]].

일괄 갱신에서 걸린 것 —

- 조건은 `{ emailVerified: { $ne: true } }` 로 쓴다. **`false` 만 찾으면
  필드가 아예 없는 문서를 놓친다** (21건 중 3건이 그랬다). 스키마에 나중에
  더한 필드는 기존 문서에 없다
- 적용 전에 **대상 목록을 눈으로 보고**, 손대지 않는 건수까지 함께 센다.
  범위가 맞는지는 "몇 건이 안 바뀌는가"로 확인된다
- 바꾸기 전 값을 백업한다. `updateMany` 는 되돌릴 정보를 남기지 않는다

### 미룬 시각은 서버에 둔다

`emailPromptSnoozedUntil` 은 회원 문서에 있다. 브라우저에 두면 기기를 바꾸거나
쿠키를 지운 사람에게 매번 다시 뜨고, 반대로 한 기기에서 미루면 다른 기기에서는
계속 뜬다. (앱 쪽 배너의 하루 미루기만 `localStorage` 다 — 링크 하나짜리라
기기별로 충분하다.)

### 공개 화면에서 안내 API를 부르지 않는다

포털 랜딩은 공개다. 안내 띠가 방문할 때마다 `/api/auth/email-prompt` 를 불러
401 을 받으면 콘솔만 시끄럽고 요청도 낭비다. `loadSession()` 이 비어 있으면
**부르지 않는다.** 쿠키를 믿어서가 아니라 부를 필요가 없어서다 — 실제 판단은
서명 토큰을 보는 서버가 한다.

### 비밀번호를 설정해도 PIN 은 지우지 않는다

전화번호로만 쓰던 사람이 이메일 인증을 마치고 비밀번호를 정해도 `pin` 은 남긴다.
지우면 여태 쓰던 로그인 방법이 갑자기 사라진다. 둘 다 가진 계정이 어느 쪽으로도
로그인되는 것은 `/api/auth/login` 이 `[password, pin]` 을 차례로 맞춰 보기 때문에
**이미 그렇게 동작한다.**

새 가입 계정은 `pin` 이 `null` 이다. 로그인이 `[u.password, u.pin].filter(Boolean)`
로 걸러 내므로 `bcrypt.compare(secret, null)` 에 닿지 않는다 — 그 필터가 곧
"`pin` 없는 계정을 건너뛴다" 는 규칙이다. **지우지 말 것.**

### 남은 과제

Snap 계열과 FitLog의 API는 아직 클라이언트가 넘기는 `userId`를 믿는다.
2hbk와 같은 방식으로 옮길 수 있다(포털은 이미 `userId`가 있는 계정에 토큰을 발급한다).
통합 admin 작업과 함께 검토한다.

> **2026-09-09 실측** — Snap 계열은 `userId` 가 아니라 **`phone` 쿼리**가 데이터 키다
> (`/api/folders?phone=`). 전화번호만 알면 남의 기록이 열리고, 전화번호 없는 새 회원은
> 빈 번호로 400 을 받는다. FitLog 는 `?userId=` 다. 계획은 [[E 개인정보 보호 보강]].

## 로컬 HTTPS 개발

```bash
npm run dev:https
```

앱마다 이 스크립트가 있다(`next dev --experimental-https`). 첫 실행 때
mkcert로 자기 서명 인증서를 만들고 `certificates/`에 둔다(`.gitignore` 등록됨).
`Secure` 쿠키·리디렉트처럼 HTTPS에서만 재현되는 동작을 확인할 때 쓴다.

단, **localhost에서는 쿠키 도메인이 적용되지 않는다.** `getEffectiveDomain()`이
`NEXT_PUBLIC_COOKIE_DOMAIN`과 현재 호스트를 비교해 맞지 않으면 도메인을 생략하기
때문이다. 서브도메인 간 세션 공유까지 로컬에서 재현하려면 `127.0.0.1`로 향하는
실제 도메인(예: `*.lvh.me`)을 써야 한다.

## 랜딩에서 로그인 상태로 갈리기

세션은 **클라이언트가 읽는 쿠키**에 있어 서버 컴포넌트에서는 알 수 없다.
포털 랜딩은 로그인 상태에 따라 갈리는 조각만 클라이언트 컴포넌트로 떼어 뒀다
(`components/LandingAuth.tsx`).

- 상태가 정해지기 전에는 **아무것도 그리지 않는다.** 로그인한 사람에게 "로그인"
  버튼이 한 번 스쳐 보이는 것보다 낫다. 헤더는 높이만 자리를 잡아 둔다
- 로그인 상태 → 우측 상단 `로그아웃`, 회원가입·히어로 버튼·마지막 CTA 시트는 감춤
