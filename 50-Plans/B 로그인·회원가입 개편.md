# B 로그인·회원가입 개편

먼저 [[인증과 세션 공유]]를 읽을 것. 이 계획은 그 구조 위에 올린다.

## 사용자가 정한 방향 (2026-09-07)

| | 지금 | 바꿀 것 |
|---|---|---|
| 회원가입 | 이메일 **또는** 전화번호 하나만 | **이메일 필수** · 전화번호 선택 |
| 로그인 | 이메일 또는 전화번호 (입력칸 하나) | **그대로 둔다** |
| 전화번호만 있는 기존 회원 | 그대로 | 이메일 등록 + 비밀번호 설정 요청 |
| 이메일 인증 | 없음 | 가입·등록 시 인증 |
| 앱별 초기값 | 없음 | 가입 후 **선택** 입력 (건너뛰기 가능) |

## ⚠️ 가장 중요한 제약 — 스키마를 필수로 바꾸면 안 된다

`users` 는 여섯 앱이 공유하는 한 컬렉션이고, 지금 `email` 은 **선택 필드**다.
전화번호만 있는 계정이 실제로 있다.

**스키마에서 `email` 을 `required` 로 바꾸면 그 계정들의 `user.save()` 가
`User validation failed: email` 로 터진다.** 다른 앱이 로그인 시각(`lastLoginAt`)만
갱신하려 해도 터진다 — [[인증과 세션 공유]] 에 같은 사고가 기록돼 있다.

> 필수는 **가입 화면과 가입 라우트에서만** 강제한다. 스키마는 선택으로 둔다.
> "모두가 이메일을 갖는" 상태는 아래 소급 수집이 끝난 뒤에야 성립한다.

## 이미 있는 것 — 새로 만들지 말 것

- **메일 발송** — `SMTP_*` 환경변수와 발송 코드가 myjane 에 있다
  (`app/api/auth/forgot-pin/route.ts` 가 토큰 링크를 메일로 보낸다)
- **토큰 흐름** — `pinResetToken` + `/reset-pin-email` 페이지가 같은 모양이다.
  이메일 인증도 이 패턴을 그대로 쓴다
- **`emailVerified` 필드** — 2hbk 가 이미 쓰고 있다. 공용으로 올려 쓴다
- **식별자 판별** — `lib/identifier.ts` (`@` 있으면 이메일, 숫자 9~11 이면 전화번호)

## ⚠️ `update-email` 라우트가 이미 있다 — 그런데 인증이 없다

`myjane/app/api/auth/update-email/route.ts` 를 **먼저 읽을 것.**
전화번호 회원의 이메일을 받는 자리가 이미 있는데 두 가지가 빠져 있다.

```ts
user.email = email;
await user.save();     // ← 인증 없이 바로 저장한다
```

- **메일 인증을 하지 않는다.** 남의 이메일을 넣어도 그대로 저장된다
- **권한 확인이 요청 본문의 `phone` + `userId` 뿐이다.**
  세션 쿠키가 아니라 클라이언트가 보낸 값을 믿는다 → 다른 사람 계정에
  이메일을 심을 수 있다

작업 3(소급 수집)은 **이 라우트를 새로 만드는 게 아니라 고치는 일**이다.
세션에서 사용자를 확인하고, 저장 대신 인증 메일을 보내도록 바꾼다.

`verify-identity` 라우트도 `phone` + `name` 으로 계정을 찾는다 — 비밀번호 찾기
흐름의 일부다. 함께 확인할 것.

## 작업 1 — 이메일 인증

```
가입/등록 → emailToken 발급(만료 30분) → 메일 발송
          → /verify-email?token=… → emailVerified: true
```

- 필드: `emailToken` `emailTokenExpiresAt` `emailVerified`
- **미인증 상태로도 로그인은 되게 한다.** 인증을 로그인 조건으로 걸면 메일이 늦거나
  스팸함에 들어간 사람이 갇힌다. 대신 앱 안에 배너로 안내한다
- 재발송에 쿨다운을 둔다(60초). 없으면 메일 폭탄이 된다
- 토큰은 **한 번 쓰면 폐기**한다

## 작업 2 — 가입 화면

이메일 필수, 전화번호 선택으로 뒤집는다. 필수/선택을 라벨에 표시한다.

```
이름            필수
이메일          필수      ← 로그인과 비밀번호 찾기에 쓰여요
비밀번호        필수      8자 이상, 영문+숫자
비밀번호 확인   필수
전화번호        선택      ← 문자로 알림을 받고 싶을 때만
```

- 전화번호를 넣으면 형식만 보고 연락처로 저장한다. **안 넣으면 건너뛴다**

> ⚠️ **계획서가 틀렸던 곳** — "전화번호를 넣으면 지금처럼 인증번호 절차를 태운다"
> 고 적었지만, myjane 에 **문자 인증 절차는 없다.** SMS 발송 코드도 인증번호
> 필드도 없다. `verify-identity` 는 `phone` + `name` 으로 계정을 찾아 주는
> 비밀번호 찾기용 조회일 뿐이다. 그래서 전화번호는 그냥 선택 입력으로 받았다.
> 문자 인증이 필요하면 발송 업체 선정부터 따로 해야 한다.
- 결쩜사처럼 `필수` 를 라벨 옆에 작게 붙인다 → [[A 디자인 요소 추가]]

⚠️ 전화번호가 없으면 `pin` 도 없다. `/api/auth/login` 은 `pin` 이 없는 계정을
건너뛰도록 이미 돼 있으니 그 로직을 **깨뜨리지 않게** 확인한다.

## 작업 3 — 전화번호만 있는 회원에게 이메일 받기

로그인은 지금처럼 전화번호+PIN 으로 되게 두고, 들어온 뒤에 요청한다.

```
로그인 성공 → email 이 없으면 → 안내 화면/배너
            → 이메일 입력 → 인증 메일 → 인증 완료
            → 비밀번호 설정 (PIN 은 남겨 둔다)
```

- **로그인을 막지 않는다.** 막으면 쓰던 사람이 갑자기 못 들어온다
- 건너뛸 수 있게 하고, 며칠 뒤 다시 묻는다(`emailPromptSnoozedUntil`)
- 비밀번호를 설정해도 `pin` 은 지우지 않는다 — 둘 다 가진 계정은 어느 쪽으로도
  로그인된다(이미 그렇게 동작한다)
- 어느 앱에서 요청할까: **포털(myjane)에서만** 한다. 여섯 앱이 각자 물으면
  같은 사람에게 여섯 번 묻는다. 앱들은 배너로 포털 링크만 보여준다

## 작업 4 — 앱별 초기 입력값 (선택)

가입 직후, 쓰려는 앱에 필요한 값을 **선택으로** 받는다.

| 앱 | 받을 것 | 없으면 |
|---|---|---|
| FitLog | 키 · 성별 · 출생연도 | 추출이 428 로 거부된다 → 그때 받는다 |
| 2hbk | 닉네임 | `userId` 로 대체 표시 |
| 나머지 | 없음 | — |

문구를 꼭 넣는다 — **"입력하지 않아도 돼요. 쓰실 때 입력해도 됩니다."**
지금 FitLog 는 프로필이 없으면 추출을 거부하는 게이트가 있다. 그 게이트는 유지하고,
가입 때 미리 받아 두면 그 순간을 안 만나게 하는 것이 목적이다.

### 소급 처리 기록 — `emailVerified` 일괄 갱신 (2026-09-07)

이미 이메일을 넣어 둔 계정은 그 주소가 맞다고 보고 인증 표시를 올렸다.
안 그러면 배포 순간 21명 전원에게 인증 안내가 한꺼번에 떴다.

```
조건   { email: 비어 있지 않은 문자열, emailVerified: { $ne: true } }
결과   matched 21 · modified 21
확인   emailVerified:true 21 · 이메일 있는데 미인증 0 · 이메일 없음 4(그대로)
```

- 3건은 `emailVerified` 필드가 **아예 없었다**(`$ne: true` 가 그것까지 잡는다).
  `false` 만 찾으면 놓친다
- 전화번호만 있는 4건은 손대지 않았다 — 그쪽은 등록부터 받아야 한다
- 되돌릴 수 있게 바꾸기 전 `_id`·`email`·`emailVerified` 를 백업했다.
  경로는 세션 임시 폴더라 **오래 두면 사라진다.** 되돌릴 일이 생기면
  `email` 이 있고 `password` 는 있는 21건이 대상이었다는 것만 기억하면 된다

> 다음에 같은 일을 할 때 — `$ne: true` 를 쓰고, 적용 전에 **대상 목록을 눈으로
> 보고**, 손대지 않는 건수까지 함께 세어 범위를 확인한다.

## C 작업에 넘기는 것 (법적 페이지)

가입 화면에 **동의 체크박스 자리만 비워 두었다.** 문구·링크가 C 의 결과물이라
먼저 만들면 두 벌이 된다.

```
자리   myjane/app/signup/page.tsx
       제출 버튼("가입하고 시작하기") 바로 위
표시   {/* ⚠️ 약관·개인정보 동의 체크박스가 들어갈 자리. … */} 주석
```

C 가 페이지를 올린 뒤 여기에 넣을 것 —

- 체크박스와 링크 (`/legal/terms` · `/legal/privacy` 등 실제 경로로)
- 필수 동의면 라벨에 `필수` 표시를 붙인다. `<Mark required />` 컴포넌트가
  같은 파일 위쪽에 이미 있다 (필수는 `--accent-ink`, 선택은 `--text-muted`)
- 동의하지 않으면 제출을 막는다. 지금 `submit()` 은 비밀번호 일치만 본다
- 동의 시각을 남길지 정해야 한다. **남기려면 `users` 스키마에 필드를 더해야 하고,
  그건 여섯 앱 `models/User.ts` 를 함께 고치는 일이다** —
  [[인증과 세션 공유]] 의 "새 필드 — 여섯 앱에 같이 넣었다" 참고

⚠️ 가입 라우트(`/api/auth/register`)는 동의 값을 **아직 받지 않는다.** 화면만
막으면 API 를 직접 부르는 쪽은 그대로 통과한다. 기록이 필요하면 라우트도 함께 고친다.

⚠️ `app/legal/*` 과 `components/LegalShell.tsx` 는 C 가 만드는 중이라 B 에서
건드리지 않았다. 확인 중에 `/legal` 이 404 였는데 **그건 정상**이다.

## 확인한 것 (2026-09-07, 사용자 답변)

| 물음 | 답 | 구현 |
|---|---|---|
| 이메일 중복 | 테스트 단계라 중복 없음 | 병합하지 않고 **409**. 유일 인덱스는 걸지 않았다 |
| 미인증 계정 | 지우지 않는다 | **하루에 한 번** 인증을 청한다 |
| 소급 수집 | 강제하지 않는다 | 같은 방식으로 **하루에 한 번**. 로그인은 막지 않는다 |

미인증 보관과 소급 수집이 결국 같은 동작("하루에 한 번 묻기")이라 필드 하나
(`emailPromptSnoozedUntil`)로 둘 다 처리했다. 미룬 시각은 **서버에 둔다** —
브라우저에 두면 기기를 바꿀 때마다 다시 뜨고, 한 기기에서 미루면 다른 기기에서
계속 뜬다.

### 실제 데이터로 확인 (2026-09-07)

```
전체 25 · 이메일 있음 21 · 전화번호만 4 · 둘 다 없음 0
emailVerified: true 0건
중복 이메일 0 · 중복 전화번호 0
인덱스 _id_ phone_1 phone_1_name_1 email_1(비유일) userId_1
```

중복이 0건이라 `email` 에 유일 인덱스를 걸 수도 있게 됐지만 **걸지 않았다.**
여섯 앱이 공유하는 컬렉션이라 기존 `email_1` 을 갈아엎어야 하고, 지금은
가입·등록 라우트에서 막는 것으로 충분하다.

기존 21개 계정이 전부 `emailVerified: false` 였다. 배포하면 그 사람들에게도 인증
안내가 한꺼번에 떴을 것이라, **2026-09-07 에 21건을 `true` 로 올렸다**
(아래 "소급 처리 기록"). 이제 안내는 전화번호만 있는 4건에만 뜬다.
