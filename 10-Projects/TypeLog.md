# 데이터 모델

여기가 이 프로젝트의 핵심이다. 처음에 잘못 잡으면 질문지가 늘어난 뒤에 고칠 수 없다.

## 무엇을 표준으로 삼았나

바닥부터 설계하지 않고, 검증된 표준에서 각각 한 층씩 가져왔다.

| 층 | 가져온 표준 | 가져온 것 |
|---|---|---|
| **정의** | HL7 **FHIR Questionnaire** | 재귀 `item` 트리 · **순서가 아닌 `linkId`** · `enableWhen` 분기 · 넓은 문항 타입 |
| **채점** | 1EdTech **QTI** (`outcomeDeclaration` + `responseProcessing`) | **결과 변수를 문항과 분리해 선언**하고, 채점을 코드가 아니라 **데이터(규칙)로** 둔다 |
| **응답** | FHIR **QuestionnaireResponse** | 답을 **순서가 아니라 `linkId`로** 저장하고 정의를 참조한다 |
| **정규화** | 심리측정의 **POMP** (Percent Of Maximum Possible) | 채점 규칙에 쓰는 숫자를 문항 수와 무관한 0~100으로 |

QTI의 결과 변수 선언이 가장 중요하다. 축(axis)·태그(tally)·총점(sum)·벡터(dim)를
각각의 필드로 두지 않고 **한 목록**에 종류만 다르게 담는다. 새 스코어링 방식이 생겨도
스키마를 안 고친다.

## 설문지의 생애주기 — 상태로 잠근다

**문항은 바뀌지 않는다. 추가되지도 않는다.**
대신 설문지를 `draft`로 만들어 두고, 확정되면 `published`로 잠근다.

```
draft (off) ──publish──▶ published (on) ──close──▶ closed
    ▲                          │
    └── unpublish (응답 0건일 때만)
```

| 상태 | 관리자 | 사용자 |
|---|---|---|
| `draft` | **JSON으로 통째로 갈아엎는다.** 문항 수정·추가·제거 전부 자유 | 목록에 안 보인다. 응시 불가 |
| `published` | 잠김 | 응시 가능. 단 `schedule`이 열려 있을 때만 (아래) |
| `closed` | 잠김 | 새 응시 불가. 지난 기록은 계속 본다 |

### draft에서는 통째로 교체한다

JSON 등록의 기본 모드는 **`upsert` 하나**다. 관리자가 부분 수정을 요청하지 않고
**전체를 다시 만들어 한 번에 붙여넣기** 때문이다.

- `slug`가 없으면 새로 만든다
- `slug`가 있고 `draft`면 **문항·outcomes·resolver·resultTypes를 통째로 교체**한다.
  옛 문항은 남기지 않는다
- `slug`가 있고 `published`면 **거부한다.** 되돌리려면 먼저 `unpublish`

예외는 `mode: "content"` 하나뿐이다 — 아래 참조.

### published가 되면 잠긴다

응답이 가리키는 문항이 사라지거나 가중치가 바뀌면 과거 결과가 조용히 거짓이 된다.
그래서 published 이후에는 문항·`outcomes`·`resolver`를 **API 레벨에서 막는다.**
관리자 화면에도 편집 버튼을 두지 않는다.

`unpublish`는 **응답이 0건일 때만** 허용한다. 한 건이라도 있으면 막고,
새 `slug`로 다시 만들라고 안내한다.

**결과 문장(`resultTypes.content`)만은 published 후에도 고칠 수 있다**(2026-09-04 결정).
응답 계산에 영향이 없기 때문이다. 오타 하나 고치려고 새 `slug`를 만들 수는 없다.
`mode: "content"`로 보내며, `code`와 `vector`는 바꿀 수 없다 — 그건 채점 결과와 이어져 있다.

### 공개 예약 — `startAt`과 오프닝 문구

`schedule`은 **"지금 이 사람이 이 문제를 풀 수 있나"만 판정한다**(2026-09-04 사용자 정정).
목록을 어떻게 그릴지는 별개이고, 판정은 **응시하려고 접근한 시점**에 한다.

**`startAt`도 `endAt`도 없을 수 있다.** 셋 다 정상 조합이다 —
둘 다 없음(바로 열려 무기한) · `startAt`만(예약 후 무기한) · 둘 다(기간 한정).

```ts
// lib/schedule.ts — 없는 값을 "제한 없음"으로 다룬다
export function canStart(schedule, now = new Date()) {
  const { startAt, endAt } = schedule ?? {};
  if (startAt && now < startAt) return { ok: false, reason: "before_start" };
  if (endAt   && now > endAt)   return { ok: false, reason: "after_end" };
  return { ok: true };
}
```

> ⚠️ **`endAt`이 없을 때 비교를 그대로 하면 항상 마감된다.** JS에서 `Date > null`은
> `null`이 `0`으로 바뀌어 **언제나 `true`** 다. `now > endAt` 한 줄만 쓰면 마감일을
> 넣지 않은 질문지가 전부 닫힌다. `startAt`은 반대로 `now < null` → `false`라
> **우연히** 동작하는데, 우연에 기대지 않고 둘 다 있는지를 먼저 본다.
> 없는 값을 `null`로 두고 **존재 검사를 앞에 붙이는 함수 하나**로 모아 둔다.

```json
"schedule": {
  "startAt": "2026-09-10T09:00:00+09:00",
  "endAt": null,
  "openingNoticeText": "9월 10일에 만나요. 어떤 동물이 나올지 기대해 주세요 🦊"
}
```

- `openingNoticeText`가 **있으면 그것을**, 없으면 **기본 문구**를 띄운다
  (기본: `곧 만나요. 조금만 기다려 주세요 ✨`)
- `startAt`이 없으면 공개 즉시 풀 수 있다
- `endAt`은 선택. 지나면 새 응시만 막고 기록 조회는 그대로 둔다
- 목록에서는 **탭을 나눈다.** 아직 안 열린 질문지에 잠긴 표시를 붙여 섞어 두지 않고
  `Coming Soon` 탭으로 따로 리스팅한다(2026-09-04 사용자 결정) — 아래 "목록 화면"
- 그래도 **막는 곳은 시작하는 순간 한 곳**이다. 탭은 보여주는 방식일 뿐이다
- 필드 표기는 **camelCase**로 통일한다. 네 앱이 전부 camelCase다
  (`measuredAt` · `imageUrl`). `start_dt`가 아니라 `startAt`

> ⚠️ **시간대.** `startAt`은 오프셋을 포함한 ISO 문자열로 받아 **Date로 저장**한다.
> `"2026-09-10T09:00"`처럼 오프셋 없이 받으면 서버(UTC)와 사용자(KST)가 9시간
> 어긋나 "오픈했는데 안 열린다"가 된다. 검증기가 오프셋 없는 문자열을 거부한다.

## 컬렉션 (3개 + 나중 1개)

문항이 안 바뀌므로 **문항 은행(`items`)을 따로 둘 이유가 없다.** 설문지 문서 안에 담는다.

| 컬렉션 | 내용 |
|---|---|
| `quizzes` | 설문지 하나 전부 — 메타 · `status` · `schedule` · `outcomes` · **`items` (embed)** · `resolver` |
| `resulttypes` | 결과 타입과 준비된 답안. `(quizId, code)` 유니크 |
| `attempts` | 응시 1회 = 답변 배열 + 계산된 결과 스냅샷 |
| `quizstats` | 집계 (나중) — 결과 분포·완주율 |

`resulttypes`를 분리하는 이유 — 결과 화면은 **1건만** 읽는다. 16종의 긴 콘텐츠를
설문지 문서에 함께 두면 목록 화면에서도 매번 따라온다. 콘텐츠만 따로 갱신하기도 쉽다.

### `quizzes` — 결과 변수를 **선언**한다

```
outcomes: [{
  id            "EI" | "lion" | "total" | "warmth"
  kind          "axis" | "tally" | "sum" | "dim"
  label         화면 표기
  left/right    kind:"axis" 일 때 — { code:"E", label:"바깥으로" }
}]
```

| `kind` | 뜻 | 정규화 |
|---|---|---|
| `axis` | 양극 축. 음수는 좌, 양수는 우 | POMP 0~100. 50이 정중앙 |
| `tally` | 단극 누적. 많이 모은 쪽이 이긴다 | POMP 0~100 |
| `sum` | 전체 총점 | POMP 0~100 |
| `dim` | 벡터 한 차원. 최근접 매칭용 | 정규화 후 벡터로 |

### `resolver` — 결과를 정하는 방법

여섯 가지 전략을 둔다. 마지막 `rules`가 **탈출구**라서 앞의 다섯으로 안 되는 케이스도
스키마를 고치지 않고 표현된다.

| 전략 | 계산 | 예 |
|---|---|---|
| `argmax` | 가장 높은 `tally`의 id를 코드로 | 나와 가까운 동물 |
| `letters` | 축마다 임계값(기본 50)으로 좌/우 letter → 순서대로 이어 코드 | 16가지 성향 |
| `nearest` | 응답 벡터와 결과 타입 `vector`의 최근접 (코사인 / 유클리드) | 나에게 맞는 영어 이름 |
| `band` | 지정한 outcome의 값이 속한 구간 | 점수형 · 단계형 |
| `matrix` | 두 축을 각각 구간으로 나눈 조합표 | 2×3 = 6타입 같은 격자형 |
| `rules` | **조건 목록을 위에서부터 평가**해 처음 맞는 코드 | 위 다섯으로 안 되는 전부 |

`rules`의 조건은 **문자열 수식이 아니라 구조**로 쓴다. 문자열을 `eval`하면 관리자가
붙여넣는 JSON이 곧 실행 코드가 된다.

```
{ "when": { "all": [ { "outcome": "lion", "gte": 60 },
                     { "answer": "q_pet", "eq": "yes" } ] },
  "code": "lion_keeper" }
```

`all` · `any` · `not` + `outcome`/`answer` 참조 + `eq`·`ne`·`gte`·`lte`·`in` 만
지원한다. 마지막 규칙은 항상 무조건 참인 기본값을 둔다.

### 답은 순서가 아니라 `linkId`로 저장한다

문항이 안 바뀌어도 이 규칙은 유지한다 —

- 문항을 **섞어서** 보여줄 수 있다 (`shuffle`)
- `enableWhen` 분기가 있으면 사람마다 답한 문항이 다르다
- 배열 인덱스로 저장하면 화면 코드의 실수 하나로 답이 통째로 밀린다

`linkId`는 **published 시점부터 영구 식별자**다. draft에서는 얼마든지 바꿔도 된다.

### POMP를 쓰는 이유 — 화면이 아니라 **JSON을 쉽게 쓰려고**

**점수를 화면에 보여주지 않는다** (아래 "기록 화면" 참조). 그래도 정규화해서 저장한다.
이유는 저작 편의와 규칙 안정성이다.

1. **`resolver`에 쓰는 숫자가 문항 수와 무관해진다.** `{ "outcome": "lion", "gte": 60 }`
   처럼 0~100으로 쓸 수 있다. 원점수를 기준으로 쓰면 문항이 10개인지 24개인지에 따라
   임계값을 매번 다시 계산해야 하고, JSON을 만드는 쪽이 그걸 틀린다
2. `letters`의 임계값 50, `band`의 구간도 같은 이유로 문항 수와 무관해진다
3. **선택 문항을 건너뛰면** 그 회차의 가능 범위가 줄어든다. 정규화가 이걸 흡수한다

`raw` · `min` · `max` · `pomp`를 **모두** 저장한다. 화면에 안 쓰더라도 나중에
규칙을 손봤을 때 재계산·검증할 수 있어야 한다. FitLog가 수치를 `{value, min, max}`로
저장해 해석 기준까지 남기는 것과 같다.

```
pomp = 100 × (raw − min) / (max − min)
```

`min`·`max`는 **그 회차가 실제로 답한 문항들**의 이론적 최소·최대다.

> ⚠️ **`min`·`max`는 "가능한 값"이지 "받은 값"이 아니다.** 어떤 축에 −2 ~ +2를 주는
> 문항이 6개면 그 축의 범위는 −12 ~ +12다. 답을 안 한 문항(선택 문항·분기로 안 나온
> 문항)은 **범위 계산에서도 빼야 한다.** 안 빼면 미답이 곧 "중간값"으로 취급된다.

### `attempts`

```
owner        { kind: "user"|"guest", userId?, guestKey? }
quizId, quizSlug, scoringVersion
attemptNo    이 사람의 이 설문지 n번째 회차
status       "in_progress" | "completed" | "abandoned"
startedAt, completedAt, durationSec
shuffleSeed  섞었다면 재현용
answers   [{ linkId, oids[], value, answeredAt, changedCount }]
result: {
  code, ranked[{ code, score }]      1등만이 아니라 순위 전체를 남긴다
  outcomes [{ id, raw, min, max, pomp }]
  confidence   1등과 2등의 격차
  engineVersion, computedAt
}
share      { token, isPublic, viewCount }
expiresAt  게스트만 (TTL). 계정으로 옮겨지면 지운다
```

`ranked`를 전체 저장하는 이유 — "아슬아슬하게 2등이었어요"가 재미 요소이고, 나중에
결과 타입을 추가했을 때 과거 회차의 순위를 다시 볼 수 있다.

## 결정 사항

### 계정 = 응시자 1명

아이별로 나누지 않는다. `attempts`는 `owner.userId`만 본다.
나중에 형제자매를 나누게 되면 기존 기록을 마이그레이션해야 한다는 것을 알고 가는
선택이다(2026-09-03 사용자 결정).

### 재응시 무제한 — FitLog와 정반대

FitLog는 `userId + measuredDate`에 유니크를 걸어 **날짜당 1건**만 둔다.
TypeLog는 **다시 하기가 기능**이므로 유니크 제약을 걸지 않고 `attemptNo`로 회차를 센다.
같은 날 세 번 해도 세 건이다.

### 결과는 코드·점수만 스냅샷하고, 문장은 최신 것을 읽는다

오타 하나 고쳤다고 과거 결과 문장이 굳어 있으면 계속 틀린 문장을 보여줘야 한다.
반대로 코드·점수를 스냅샷하지 않으면 결과 타입을 손본 뒤 "그때 무슨 결과였는지"를 잃는다.
그래서 `attempts.result`에는 코드·점수·순위를 남기고, 화면 문장은 `resulttypes`에서 읽는다.

### 문항 등록은 JSON 붙여넣기 + 기계 검증

관리자가 문항을 하나하나 화면에서 넣지 않는다. **AI가 규격에 맞는 JSON을 만들고,
관리자는 붙여넣기만 한다.** 세부는 사람이 아니라 검증기가 확인한다
→ [[설문지 JSON 작성 지침]]

FitLog가 인바디 합계 규칙으로 Vision의 숫자 오인식을 잡는 것과 같은 장치다.
**사람이 검토하지 않는 입력은 기계가 검사할 수 있는 형태여야 한다.**

### 게스트 응시 — 설문지당 1회, 이관은 확실한 순간에만

공유 링크로 들어온 사람은 로그인 없이 응시할 수 있다.
클라이언트 구분값(`guestKey`, localStorage UUID)으로 진행 상태를 잇는다.

- **한 `guestKey`는 한 설문지를 1회만** 응시할 수 있다(2026-09-04 사용자 결정).
  안 막으면 원하는 결과가 나올 때까지 돌린다. 다시 하려면 가입해야 한다
- 회원은 무제한 재응시 그대로다
- `guestKey`는 localStorage에 있으므로 **지우거나 시크릿 창을 열면 다시 할 수 있다.**
  막을 방법이 마땅치 않고, 막으려고 IP·지문을 쓰는 것은 과하다. 한계로 둔다

결과 화면 문구 (사용자 지시, 그대로) —

> 가입하여 나의 타입을 기록해요.
> 가입하지 않으면 기록은 다시볼 수 없어요.

### ⚠️ 이관은 "확실히 매칭되는 순간"에만 한다

가입하면 방금 한 응시를 계정으로 옮겨 준다. 미가입 장바구니를 가입 후 넘겨주는 것과
같은 개념이다. 단, **아무 때나 옮기지 않는다.**

로그인할 때마다 `guestKey`를 훑어 옮기면, 그 브라우저를 누가 썼는지 알 수 없는 기록까지
계정에 붙는다(가족 공용 PC, 남에게 빌려준 폰). **그래서 결과 화면에서 가입·로그인으로
바로 이어진 그 흐름에서만** 옮긴다(2026-09-04 사용자 결정).

```
결과 화면 [가입하고 기록하기]
  → 서버가 그 응시 1건에 대한 1회용 claimToken 을 발급 (짧은 만료, 예: 30분)
  → 포털 가입·로그인으로 보내고 next 에 실어 되돌아온다
  → POST /api/attempts/claim { claimToken }  → 그 1건만 계정으로 옮긴다
```

- `guestKey` 전체를 스윕하지 않는다. **토큰이 가리키는 응시 1건만** 옮긴다
- 토큰은 1회용이다. 이미 쓴 토큰·만료된 토큰은 조용히 무시한다
- 옮기는 대상은 `completed`만. 진행 중이던 것은 게스트로 두고 만료시킨다
- **`attemptNo`를 다시 매기는 것을 빠뜨리기 쉽다.** 게스트로 1회차였던 기록이 계정에
  이미 2건 있는 설문지로 들어오면 3회차가 되어야 한다. 옮긴 뒤 `startedAt` 순으로 재부여
- 옮기면 `guestKey`와 `expiresAt`을 `$unset` 한다
- 이 흐름을 타지 않은 게스트 기록은 **옮기지 않고 만료된다.** 그래서 결과 화면 문구가
  "가입하지 않으면 기록은 다시볼 수 없어요"인 것이다 — 사실과 맞는 문장이다
- 게스트 `attempts`의 TTL은 **30일**. TTL은 **부분 인덱스**로 건다 — 회원 문서에는
  이 필드가 없어야 하고, sparse로 두면 회원 기록까지 지워질 위험이 있다

### 공유 링크는 헤더 없이 문제만 보여준다

`/r/[token]`은 **TopNav·푸터·앱 스위처 없이** 질문지만 그린다. 처음 온 사람에게
네비게이션은 방해다(2026-09-04 사용자 결정).

### 그 밖에 정한 것 (2026-09-04)

| 항목 | 결정 |
|---|---|
| 공개 후 결과 문장 수정 | **허용한다.** 응답 계산에 영향이 없다. `mode: "content"` 하나만 남긴다 |
| 도감 | 회차마다 나온 타입을 **전부 모은다.** 최신 것만 두면 도감이 비어 보이고, 다시 하기의 보상이 사라진다 |
| 진행 중 저장 | **매 문항마다 서버에 저장한다.** 아이가 중간에 나간다. 이어하기·게스트 이관에 모두 유리하다 |
| 결과 공유 OG 이미지 | 만든다. 결과 타입 이모지 + 이름 카드. `@vercel/og`면 R2 없이 된다. **2차** |

### 결과 문장은 **해요체** — 결쩜사 톤을 지킨다

아이 대상이라고 반말로 쓰지 않는다(2026-09-04 사용자 정정).
문장은 [[결쩜사 카피 톤앤매너]]를 그대로 따른다.

- **전부 해요체.** `~합니다`(격식)도 `~한다`(단정)도 쓰지 않는다
- 짧게 끊고 줄바꿈으로 호흡을 만든다. 한 줄에 다 넣지 않는다
- **숫자로 증명하지 않는다.** 점수·확률·등급·"상위 몇 %" 같은 계량 표현을 쓰지 않는다.
  기록 화면에서 그래프를 뺀 것과 같은 이유다
- 단정하지 않는다. "당신은 ~입니다"가 아니라 "~한 편이에요"
- eyebrow는 명사형 영문 한두 단어 (`RESULT` · `YOUR TYPE` · `RECORDS`)

```
어울리는 건 이런 순간이에요.
사람이 많은 자리보다,
마음 맞는 한 사람과 보내는 시간요.
```

## 목록 화면 — 탭을 나눈다

아직 안 열린 질문지를 잠긴 카드로 섞어 두지 않는다. **탭으로 분리해 따로 리스팅한다**
(2026-09-04 사용자 결정). 섞어 두면 목록을 훑다 잠긴 카드를 계속 만나 김이 샌다.

| 탭 | 담기는 것 | 정렬 |
|---|---|---|
| **지금 해보기** | `published` + `startAt`이 지났고 `endAt` 전 | `order` |
| **Coming Soon** | `published` + `startAt`이 아직 안 됨 | `startAt` 오름차순 — 가장 빨리 열리는 것이 위 |

## 기록 화면 — **그래프를 쓰지 않는다**

FitLog에서 가져오는 것은 **디자인뿐**이다(2026-09-04 사용자 지시).
추이 그래프·레이더는 이 앱에 맞지 않는다. 성향에는 "늘었다·줄었다"로 읽을 수치가 없고,
숫자로 증명하지 않는 것이 결쩜사 톤이기도 하다 → [[결쩜사 카피 톤앤매너]]

**지난 기록을 다시 볼 수 있으면 된다.**

| 블록 | 내용 |
|---|---|
| 타입 도감 | 지금까지 나온 타입을 카드로 모은다. 안 나온 건 실루엣 |
| 회차 타임라인 | `1회 🦁 사자 · 2회 🐬 돌고래 · 3회 🐬 돌고래` — 날짜 + 결과 배지 줄 |
| 변화 한 줄 | 바뀐 지점에 "이번엔 다른 타입이 나왔어요" · 같으면 "지난번과 같아요" |
| 지난 결과 다시 보기 | 회차를 누르면 그때 결과 카드를 그대로 |

**회차 목록은 최근 20건 + `더 보기`** 다(2026-09-04 결정). 버튼을 누를 때마다 20건씩
더 불러온다. 목록 API는 `limit` 기본 20 · 최대 100으로 두고 `cursor`(또는 `skip`)를 받는다.
한 사람이 같은 질문지를 수십 번 다시 하면 목록이 끝없이 길어지고, 한 번에 다 받으면 느려진다.

수치가 아니라 **타입이 바뀌었는지**로 변화를 말한다. 그래프 컴포넌트를 이식하지 않으므로
`TrendChart.tsx` · `BodyRadar.tsx`는 가져오지 않는다.

- [ ] 답 diff("3번 질문에서 마음이 바뀌었어요")는 **초기 범위에서 뺀다.**
  회차 목록을 써 보고 필요해지면 그때 검토

## 함정 (예상 — 겪으면 사실로 옮긴다)

- **`startAt`에 오프셋이 없으면 9시간 어긋난다.** 검증기가 막는다
- **`endAt`이 `null`인데 `now > endAt`을 그대로 쓰면 전부 마감된다** (`null` → `0`).
  `canStart()` 하나로 모아 존재 검사를 먼저 한다
- **published 잠금을 API에서 막지 않으면** 화면만 막아 놓은 셈이라 뚫린다
- **게스트 이관 때 `attemptNo`를 다시 매기지 않으면** 회차 번호가 겹친다
- **TTL을 sparse로 걸면 회원 기록까지 지워진다.** 부분 인덱스로 건다
- **미답 문항을 min/max에서 빼지 않으면** 안 한 답이 중간값으로 취급된다
- **동점 규칙을 미리 정하지 않으면 결과가 무작위처럼 보인다.** `tiebreak`를 필수로 둔다
- **문항·선택지를 섞으면 재현이 안 된다.** 섞을 거면 `shuffleSeed`를 저장한다
- **아이는 끝까지 하지 않는다.** `in_progress`로 이어서 하기를 지원하고, 기록·도감·통계에는
  `completed`만 넣는다
- **가중치를 화면에 내려보내지 않는다.** `lib/quizPublic.ts` 의 `publicItem()` 만 쓴다.
  내보내면 원하는 결과가 나오는 답을 브라우저에서 계산할 수 있다
- **Next 의 route 파일은 핸들러와 정해진 설정만 export 할 수 있다.** 헬퍼를 함께
  export 하면 `tsc` 는 통과하는데 `next build` 가 타입 오류로 막힌다

### 추천 연령을 목록에 보여준다

질문지가 늘면서 대상이 갈렸다 — 공룡·요정은 5세부터, 명품 브랜드는 13세부터다.
`quiz.ageRange` 는 처음부터 있었지만 **화면에 안 나오고 있었다.** 그러면 아이가
자기와 안 맞는 질문지를 붙잡고 있다가 무슨 말인지 몰라 그만둔다.

| 한 것 | 어디 |
|---|---|
| 형식을 한 곳에 (`6~12세` · `13세 이상` · `10세까지`) | `lib/ageRange.ts` 의 `ageLabel()` |
| 나이대 묶음으로 거르기 | 같은 파일의 `AGE_BANDS` · `inBand()` |
| 카드 맨 앞 알약 + 필터 칩 | `app/(app)/types/page.tsx` |
| 추천 연령 **필수**로 검사 | `lib/quizValidate.ts` |

- 나이를 한 살씩 고르게 하지 않는다. 아이가 자기 나이를 눌러 **빈 목록**을 본다.
  실제로 갈리는 지점(입학 전 · 초등 저·고학년 · 중학생 이상)으로 묶는다
- 묶음은 **겹침**으로 판정한다. 포함(`min >= from && max <= to`)으로 보면
  6~13세 질문지가 어느 묶음에도 안 걸려 사라진다
- 아무것도 안 남는 묶음은 **누를 수 없게** 한다. 칩에 개수를 함께 적는다
- 범위가 10살을 넘으면 경고한다 — `6~19세` 는 아무 말도 하지 않는 것과 같다

### 실제 브랜드 이름을 결과로 쓸 때

캐릭터(디즈니·마블)와는 성질이 다르다. 캐릭터는 저작물을 **복제**하는 것이지만,
브랜드 이름은 그 브랜드를 **가리키는** 쓰임이다. 그래서 이름 자체는 쓰지만
네 가지를 지킨다.

1. **로고·서체·제품 사진을 쓰지 않는다.** 이름과 이모지만 쓴다
2. `quiz.disclaimer` 를 붙인다 — 목록 카드와 결과 화면 아래에 작게 나온다
3. 브랜드의 좋고 나쁨을 말하지 않는다. **사실로 확인되는 것**(창업 배경 ·
   대표적인 디자인 요소 · 무엇을 위해 만들어졌는지)만 근거로 쓴다
4. 사라고 하지 않는다. 결과 문장은 나에 대한 이야기다

나라 이름도 같은 장치를 쓴다. 근거는 **환경·생활 방식**(기후 · 자연 · 도시 밀도 ·
이동 수단 · 식문화)만 쓰고 "어느 나라 사람은 어떻다" 는 쓰지 않는다 — 사실이
아니고, 아이가 읽는 글이다.

### 저작권이 있는 캐릭터를 쓰지 않는다

"디즈니 공주 / 디즈니 왕자 / 어벤져스 캐릭터" 는 인기 있는 포맷이지만 **상표와
저작권이 살아 있다.** 상용 서비스에 이름을 그대로 올릴 수 없다. 재미를 잃지 않고
바꾸는 방법은 두 가지다.

| 원하던 것 | 대신 쓴 것 | 근거 |
|---|---|---|
| 디즈니 공주·왕자 | **원작 동화** 인물 (신데렐라 · 백설공주 · 인어공주 · 라푼젤 · 잠자는 숲속의 공주 · 엄지공주 / 잭 · 알라딘 · 피노키오 · 로빈 후드 · 피터 팬 · 헨젤) | 그림·안데르센·페로·천일야화·콜로디·배리 원작은 저작권 만료. 디즈니의 **묘사**만 보호된다 |
| 어벤져스 캐릭터 | **창작한 초능력 유형** (하늘 날기 · 괴력 · 투명 인간 · 시간 멈추기 · 마음 읽기 · 순간 이동) | 초능력 자체는 누구의 것도 아니다. 아이들이 궁금해하는 것도 "내가 어떤 힘을 갖게 될까" 쪽이다 |

같은 이유로 화면에 "MBTI" 를 쓰지 않는다(위 절 참고).

### 질문지 균형은 손으로 맞추지 않는다

6타입 · 10문항 · 3지선다 질문지는 **문항이 어떤 타입 셋을 가르는지를 고정 패턴**으로
두고 내용만 채운다. 각 타입이 정확히 5개 문항에 등장해서 POMP 의 분모가 같아진다.

```
PATTERN = [(0,1,2),(3,4,5),(0,2,4),(1,3,5),(0,3,4),
           (1,2,5),(0,1,3),(2,4,5),(0,2,5),(1,3,4)]
WEIGHTS = [2, 3, 5, 2, 7, 3, 5, 2, 7, 3]
```

> ⚠️ **문항 가중치를 전부 같게 두면 동점이 결과를 정한다.** 모든 문항이 2점이면
> 타입 점수가 0·2·4·6·8·10 여섯 가지뿐이고, 무작위 응답의 **36.8%** 가 1·2등 정확히
> 동점이 된다. 그러면 `tiebreak` 배열 순서가 결과를 정하므로 분포가 배열 그대로
> 줄을 선다 (`my-color` 첫 판: red 26.9% … pink 10.4%).
> 가중치를 문항마다 다르게 하면 **균형은 깨지지 않는다** — POMP 는 자기 분모로
> 나눈 값이라 `E[POMP] = 1/3` 로 모두 같다. 동점률 36.8% → **0.6%**, 분포 14~19%.

> ⚠️ **"이웃 타입에 1점" 은 균형을 깬다.** 동점을 줄이려고 선택지마다 이웃 타입에
> 1점을 더해봤는데(순환 치환), 같은 문항 안에서 이웃이 다른 선택지의 주 타입과
> 겹치면 그 타입만 기대값이 올라간다. 동점률은 9.6% 로 내려갔지만 red 26.3% ·
> green 8.3% 로 다시 벌어졌다.

`nearest` 는 함정이 두 개 더 있다 → [[설문지 JSON 작성 지침]]
